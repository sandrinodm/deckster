Use this page to look up the exact arguments and flags of a `deckster` command. Each section shows the command's summary, its usage lines and, folded, the full `deckster <command> --help` as `@deckster/cli` 0.10.1 prints it. `deckster --help` lists the commands in the same order:

```console
$ deckster --help
Usage: deckster <command> [options]

Commands:
  dev         Serve a deck with hot reload
  present     Open a deck in its own window, with displays and presenter view
  electron    Download, update or check the Electron binary deckster present uses
  build       Build a deck (or every deck) to decks/<deck>/dist
  preview     Serve the built output of a deck
  shot        Write PNG screenshots of slides (and steps)
  diff        Show which slides changed visually against a git ref or baseline
  export      Export a deck to PDF, PNG and PowerPoint
  lint        Check a deck for schema errors, overflow, contrast and off-brand values
  layouts     List the layouts available to a deck
  icons       List the icon names every brand has
  charts      List the chart and number components and when to use each
  diagrams    List the diagram components, node kinds, cards and animation primitives
  components  List the code, media, link and demo components with their props
  brand       Print a brand's resolved tokens, or check a brand
  new         Create a deck, or add a slide to one
  types       Write tsconfig.json so editors and tsc resolve @deckster imports
  comments    List, resolve, reopen, add and prune review comments
  mcp         Print Claude Code and Codex configuration for a running deckster dev --mcp
  agent       Check the agent CLIs (Claude Code, Codex): installed, version, signed in

Run `deckster <command> --help` for the options of one command; `--version` prints the version.
```

## Shared conventions

**Workspace.** Every command works in one workspace: the folder `DECK_ROOT` names, else the nearest folder at or above the current one that contains `decks/`, else the current folder (so `deckster new` can start a workspace in an empty folder). When the workspace is not the current folder, the CLI prints `Using the workspace <path>` on standard error. It never picks your home folder or `/` on its own, and exits with 1 (your home folder's path appears where `/Users/you` is):

```console
$ cd ~ && deckster layouts
/Users/you is a home or root folder, so deck will not use it as a workspace: a deck's dev server would sit next to your keys and tokens.
Make a project folder (`mkdir talks && cd talks`) and run the command there, or set DECK_ROOT to the folder you mean.
```

**Deck name.** A deck is named by its folder under `decks/`. When the deck argument is left out, `dev` and `present` use a nonempty `DECK`, open the only deck, or show the chooser when several decks exist. `layouts` uses `DECK`, then `hello` if present, then the workspace's only deck. `preview` and `mcp` use `DECK`, else `hello`, so name the deck when the workspace has no `hello`. `build` builds every deck (or the one in `DECK`). Others, such as `deckster lint`, need the deck named and print `Which deck? Name one, for example` and an example when it is missing.

**`--brand <name>`.** On `dev`, `present`, `shot`, `lint`, `diff` and `export` it renders with `brands/<name>` instead of the brand in `deck.config.ts`. On `new` it is the brand written into the new deck's config, and on `icons` it takes a comma-separated list of brands to share names between.

**`--json`.** A command that takes `--json` prints its result as indented JSON on standard output. When `shot`, `diff`, `export`, `lint`, `icons`, `brand`, `comments`, `mcp`, `agent` or `present --list-displays` fails with `--json`, it prints the failure there too and exits with 1:

```console
$ deckster lint nope --json
{
  "ok": false,
  "error": {
    "type": "DeckBuildError",
    "message": "No such deck in decks/nope:\n  - There is no decks/nope/deck.config.ts.\n    Fix: Use one of: launch-review; or create decks/nope/deck.config.ts."
  }
}
```

`type` names the kind of failure: `CliError` for a bad command line, `DeckBuildError` for a deck that does not exist or does not load, and others such as `BrandError` and `BrowserError`. A deck that cannot render also carries its lint `findings`. The catalog commands (`layouts`, `charts`, `diagrams`, `components`) print a failure as text on standard error, with or without `--json`.

**Exit codes.** `0` on success; `1` when the command fails, lint reports errors, or `deckster diff --fail-on-change` finds a change; `129` when the terminal closes (`SIGHUP`). Ctrl+C, `SIGTERM` and `SIGHUP` close the servers and browsers a command started before it exits.

**Environment variables.**

| Variable | What it sets |
| --- | --- |
| `DECK_ROOT` | The workspace folder, so you can run `deckster` from anywhere. Empty counts as unset. |
| `DECK` | The deck a command uses when none is named. Empty counts as unset. |
| `DECK_AUTHOR` | The name new comments and resolutions are signed with. Without it, git's `user.name`, else `Reviewer`. |

## deckster present

<CliCommand name="present" />

**New in v0.7.0.** `deckster present` uses the same deck-selection order as `deckster dev`. With several decks and neither a name nor `DECK`, it opens the gallery in Deckster, or in your browser with `--browser`. See [Choose a deck in the desktop gallery](/present/deck-present-and-displays/#choose-a-deck-in-the-desktop-gallery).

## deckster electron

<CliCommand name="electron" />

**New in v0.9.0.** npm, pnpm and yarn often skip Electron's download when they install `@deckster/cli`. Run `deckster electron install` once after installing, and `deckster electron update` after upgrading the CLI. `status` exits with 1 when there is no usable binary, so a script can check before a talk. See [Download Electron's binary once](/present/deck-present-and-displays/#download-electrons-binary-once).

### Code layout subcommands

<Aside type="note" title="Not in v0.10.1">
The four subcommands below are on the `main` branch and ship in the next release. The `--help` above is what 0.10.1 prints and does not list them. The guides start at [code layouts](/brands/code-layouts/).
</Aside>

The words `new`, `check`, `eject` and `diff` after `deckster layouts` start a subcommand, so a deck with one of those names is listed with `DECK=<name> deckster layouts`. All of them take `--json`. Exactly one of `--brand` and `--deck` is required, and the brand must be a folder of the workspace, not the built-in `default`.

```sh
deckster layouts new <name> (--brand <brand> | --deck <deck>)
deckster layouts check [<name>] (--brand <brand> | --deck <deck>)
deckster layouts eject <name...> (--brand <brand> | --deck <deck>) [--keep-shared]
deckster layouts eject --all --brand <brand> [--keep-shared]
deckster layouts diff <name> (--brand <brand> | --deck <deck>) [--fail-on-change]
```

- **`new`** writes `layouts/<name>/` in the brand or the deck with four files that pass `layouts check`, `brand check`, `lint` and the build as written: `contract.ts` with one `body` slot, a required title, an eyebrow, an example and a PowerPoint mapping; `layout.tsx`; `layout.css`; and `limits.ts` with one case, `full-body`. It prints the files and a `Next:` line. With `--json` it prints `{ ok, layout, brand, deck, dir, files, next }`. It refuses, and writes nothing, for a name that is not kebab-case (at most 64 characters), a folder that exists, a kit or engine layout, a data layout of the brand, for a deck a code layout of the deck's brand and a path that runs through a symbolic link.
- **`check`** checks the contracts, imports and replacements of the brand's or deck's code layouts, or of the one named, then renders each layout without an error and lints the result. It exits 0 when no layout has an error and 1 when one does or the command fails. With `--json` it prints `{ ok, brand, deck, dir, layouts: [{ name, dir, cases, ok, problems }], problems }`; each problem is `{ severity, code, file, message, fix, case?, slide?, step?, selector? }`, and the top-level `problems` belong to no one layout, such as `layout-version`. [Check a code layout](/brands/code-layout-checks/)
- **`eject`** copies kit layouts into the brand or deck as code layouts that replace them, with `--all` for every kit layout the brand has no folder for. It prints the files, the helpers it reused or kept and a `Next:` line. With `--json` it prints `{ ok, brand, deck, layouts: [{ name, dir, files }], shared: { written, reused, kept }, skipped, skippedForDecks, warnings, next }`. [Replace a kit layout](/brands/replace-a-kit-layout/)
- **`diff`** prints a unified diff of what the kit changed in an ejected layout since you ejected it, on standard output. It exits 0, or 1 with `--fail-on-change` when the kit changed the layout or it no longer ejects cleanly, and 1 for a layout with no `.eject/eject.json`. With `--json` it prints `{ ok, brand, deck, layout, dir, ejectedWith, current, changed, files: [{ path, status, diff }], problems, provenanceEdited }`.

In the same release `deckster layouts` and `deckster brand` also report code layouts: a layout's `source` is `brand-code:<brand>` or `deck:<deck>`, a replacement carries `replaces`, and `deckster brand <name>` prints a `Code layouts:` line.
