A code layout is code that runs on your machine: its contract runs in Node and its component runs in your browser. This page draws the line deckster keeps around it: `deckster brand add` never copies code, an agent turn cannot write or load a layout, and a layout reaches your workspace only when you copy it there.

<Aside type="note" title="New in v0.11.0">
Code layouts shipped in 0.11.0. Earlier versions copy data only in `deckster brand add` too, and ignore a `layouts/<name>/` folder.
</Aside>

## Fetched brands carry data, not code

`deckster brand add` copies `brand.ts`, `layouts.ts`, images, fonts and documents, and runs none of it. Code layouts, meaning `layouts/<name>/` folders with a `contract.ts` or `layout.tsx`, and every other code file are left out and listed under `Left out:`. A layout's whole folder is left out, so its README and images are listed as `code layout` too, and a half-copied layout never reaches the brand. [Add a brand from another repository](/brands/use-a-brand/#add-a-brand-from-another-repository) covers the rest of what it copies.

The command always writes `brands/<name>/.deckster-source.json` with three keys: `source`, where the brand came from, without credentials; `commit`, the commit it fetched, or `null` when unknown; and `codeLayoutsSkipped`, the sorted names of the code layouts it left out, such as `["kpi-wall"]`. Adding the brand again replaces the file, and a `.deckster-source.json` inside the fetched brand is ignored. With `--json` the same names are under `codeLayoutsSkipped`, and `written` lists the file.

A data layout in `layouts.ts` that falls back to a skipped code layout is added with a warning, because its bindings cannot be checked until the folder is copied.

A slide that uses a skipped layout fails with `layout-code-skipped`. The message names the layout, says that `deckster brand add` left it out and gives the source to read.

## Bring one in yourself

1. Read the code in the brand's own repository. It runs on your machine, in Node and in the browser, with your files and your login.
2. Copy its `layouts/<name>/` folder, and what it imports from `layouts/_shared/`, into `brands/<name>/layouts/`.
3. Run [`deckster layouts check --brand <name>`](/brands/code-layout-checks/).

A brand shared inside a team's own repository never goes through `deckster brand add`: its folder is already yours.

## Agent turns cannot write or load layouts

The chat agent in `deckster dev --agent` may change only a deck's slide files and its `assets/` and `public/` content. Layouts, contracts, brands and stylesheets are off limits, like every other code file the dev server runs. It can read the code layouts through its `catalog` tool and use them in slides. See [how a turn runs](/ai-agents/how-a-turn-runs/).

While a turn runs, the code layouts of the deck and of its brand are held:

- A `contract.ts` or `limits.ts` there is not read or evaluated again until the turn is over, so an agent cannot change what the build runs by editing one.
- The agent sees the last version loaded before the turn.
- A contract that was never loaded before the turn starts fails with `layout-held`.
- A turn that begins while a contract is loading stops it from loading any more modules, and deckster drops whatever that load produced. Code of it that is already running after an `await` finishes, but its value is not used; the contract loads again once the turn ends.

Write layouts in your editor, or with a coding agent that works in your workspace, outside the chat panel. [Skills](/ai-agents/skills/) covers the agents that do.

## What each import check guards

The build reads a contract and the relative files it imports as text before it runs anything, and rejects an import outside the [allowed list](/brands/code-layouts/#what-each-file-may-import). The check keeps a contract to the framework's entry points and the layout's own folder. It is a gate on imports, not a sandbox: a contract is code that runs in Node with your permissions, so treat a layout from elsewhere as you would any script. A layout you copied in is code like a slide or a mini app, and the [security page](/project/security/) says how to treat those. The line deckster draws is who may put code in the folder, not what that code may do once it is there.

Before a contract runs in the build, deckster first runs it in a separate Node process under Node's permission model, with a deadline. That process stops a contract that hangs or loops, and one that writes files, opens network connections, starts processes, changes the environment or imports something outside the allowed list, and reports it. It catches mistakes early; it is not a sandbox either. A contract that passes runs again in the build with your full permissions, and code that behaves differently there is not caught.
