Use this page to understand why deckster is built the way it is, before you adopt it for a team or change its code. Each section gives the reason for one choice and links to the page that explains how it works.

## Four ideas

Agents write most of the slide content, and the result should still look designed. Four ideas carry that:

1. **A brand is data.** A brand is a typed token file plus its assets. Slides hold no raw colours, fonts or pixel positions. See [brands and surfaces](/concepts/brands-and-surfaces/).
2. **Slides fill typed layouts.** You pick a layout and fill its slots; the layout owns the type, the grid and the spacing, so a slide cannot go off-brand without the linter saying so. See [layouts and slots](/concepts/layouts-and-slots/).
3. **Agents see their own work.** `deckster shot` renders any slide to a picture and `deckster lint` reports overflow, contrast, off-brand values and content over budget, each with its fix. Without that loop an agent cannot tell a good slide from a broken one. See [lint as the contract](/concepts/lint-as-the-contract/).
4. **One React tree.** Diagrams, code, video and live mini apps are components on the slide, driven by one step counter.

## An engine of its own

The engine is a React runtime on Vite, not a layer over an existing slide framework, because of the step counter. A slide's step is React state, and diagrams, charts and code animations read it with `useStep()`. A framework that keeps reveal steps as classes on the page would give those components a second source of truth, and one built on another UI library would push every React component into an iframe.

## One file per slide, in MDX, listed in the config

- **MDX, not plain Markdown.** Slides need components, and Markdown extensions end up as a worse component system.
- **MDX, not HTML.** HTML has no schema to validate and invites inline styling.
- **One file per slide.** Diffs stay small, several authors or agents can work at once without conflicts, and a review comment maps to exactly one file.
- **The config lists the order.** Moving a slide is a one-line change in `deck.config.ts`, not a rename of numbered files.

See [decks and slides](/concepts/decks-and-slides/).

## A fixed 1920 by 1080 canvas

Every slide is laid out on a 1920 by 1080 canvas scaled to the window, and type sizes are canvas pixels from the brand's scale. A slide therefore looks the same at every window size, in a screenshot and in an export. See [static mode and readiness](/concepts/static-mode-and-readiness/).

## Diagrams by grid cell, and no Mermaid

`<Flow>` places nodes by column and row, because agents are reliable with grid cells and unreliable with pixel coordinates. Every diagram is drawn by the kit, with no Mermaid tier: a diagram the kit draws takes the brand's colours and type, reveals by step, and can be checked by `deckster lint`. See [flow diagrams](/data-and-diagrams/flow-diagrams/).

A brand also styles its diagrams, down to named node styles called cards. Five card names exist in every brand, so a slide that marks its key node `card="solid"` renders in any brand, each in its own way. A name a brand lacks falls back to another card instead of failing the build, because a deck may be rendered in another brand, and `deckster lint` reports it. See [diagram look and cards](/brands/diagram-look-and-cards/).

## Charts that lead with a highlight

Every chart takes a `highlight`, what matters, and mutes the rest; the slide title states the takeaway and the chart supports it. Labels sit on the marks instead of in a legend where they can. Each chart is planned from its rows into shapes and text without a browser, which is also what lets an export write it as a native PowerPoint chart. See [highlights and annotations](/data-and-diagrams/highlights-and-annotations/).

## Code highlighted at build time

Code is highlighted when the deck builds, with colours written as CSS variables, so one highlight fits every brand and every surface. See [code](/write-slides/code/).

## Review comments as committed files

A comment made in the dev server is saved as a file in the deck, with the source file and line of the element it points at. Comments therefore show up in code review and in history, and an agent can list them, fix the slide and resolve them from the terminal. The cost: a built deck has no comment overlay, since commenting on a static site would need a backend. See [comments](/review/comments/).

## A native PowerPoint writer

`deckster export --pptx` writes the PowerPoint file itself instead of pasting pictures of slides. Text, shapes, tables, pictures, notes and links are native wherever a slide can be expressed that way, and charts and diagrams become native charts, shapes and connectors, so the result stays editable. Because an editable slide never matches the web slide exactly, the export can list what it drew natively and score the file against the web slide. See [PowerPoint](/export-and-publish/powerpoint/).

## Electron for `deckster present`

`deckster present` opens an Electron window because Electron renders with Chromium on every platform, the same engine family `deckster lint`, `deckster shot` and the exports use. A shell on the system webview would render in WebKit on macOS and Linux, and lint would no longer describe what the audience sees. See [`deckster present` and displays](/present/deck-present-and-displays/).

## The agent's own CLI, not a bundled model

The agent panel runs the `claude` or `codex` CLI you installed, one process per turn, with the login you already have. deckster bundles no model and no SDK; stopping a turn is a signal to that process; and each provider is a small adapter, so the panel and the checks after each turn are the same for both. The same deck tools reach any agent you run in a terminal over MCP. See [how a turn runs](/ai-agents/how-a-turn-runs/).
